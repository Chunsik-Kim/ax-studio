개발·SI·사업운영 경험을 바탕으로 실제 업무를 AI Workspace와 Agent 기반 Workflow로 구조화하고, 다양한 프로젝트에 적용하며 고도화하고 있습니다.

AI/AX 시스템 설계 · 업무자동화 · AI Agent · AI-native Workflow

웹개발자로 시작해 SI/SM 중심 IT기업을 10년 이상 운영했고, 이커머스·콘텐츠·스타트업 서비스 기획을 직접 경험했습니다. 현재는 이 경험을 AI/AX 업무시스템 설계와 자동화로 연결하고 있습니다.

Web Development→ SI/SM & IT Business→ Commerce / Content→ Service Planning→ AI / AX
Why

왜 이런 구조를 만들기 시작했나

웹개발자로 시작해 SI/SM 프로젝트, IT기업 운영, 영업, 고객관리, 사업기획을 거치며 기업 업무는 분리된 Task가 아니라 연속된 프로세스라는 걸 경험했습니다.

생성형 AI로 처음엔 바로 코딩부터 시작했지만, 실제 서비스에는 '무엇을 왜 만드는가, 사용자가 왜 쓸 것인가, 사람이 판단할 부분은 무엇인가, 결과를 어떻게 검증할 것인가'가 코딩보다 먼저 필요하다는 걸 실제 프로젝트에서 겪었습니다.

그 결과 업무영역별로 Context와 역할을 분리한 AI Workspace 구조를 하나씩 발전시켜 왔습니다.

How

업무를 AI와 사람이 함께 수행하는 구조로 바꾸는 방법

완성된 독점 방법론은 아닙니다. 실제 운영 경험과 다양한 AX 사례연구를 통해, 현재 다음과 같은 실무적 접근으로 구조화해서 쓰고 있습니다.

도구를 먼저 선택하지 않고, 업무 특성과 제약조건을 먼저 정의합니다.

UNDERSTAND → EVIDENCE → DECOMPOSE → DECIDE → DESIGN → PILOT → EVALUATE → APPROVE → LEARN → STANDARDIZE

이 접근을 실제 워크스페이스로 구현한 대표 사례가 AX-ARCHITECT의 6단계 진단 방법론(DEFINE→EVIDENCE→DIAGNOSE→DESIGN→EVALUATE→PROVE)이며, 지금까지 13개 사례에 실제 적용했습니다.

Current System

현재 AI Workspace 아키텍처

워크스페이스가 늘어나면서 각각의 규칙이 달라지고, 스킬이 분산되고, Claude와 Codex 간 인수인계가 필요해지고, 변경사항 전파와 상태 점검이 필요해졌습니다. 이 문제를 풀기 위해 상위 관리계층(ATLAS)을 구축해 워크스페이스 생성 자동화, 세션 인수인계 프로토콜, 크로스 워크스페이스 감사, 스킬 라이프사이클 관리를 표준화했습니다.

15개 이상의 Domain Workspace를 구축하고 업무별로 운영·실험하고 있으며, 완성도와 실사용 수준은 워크스페이스마다 다릅니다.

AX-ARCHITECT — 업무를 AX 관점에서 어떻게 진단하는가

Diagnosis
문제
업무를 바로 수정하면 근거 없는 판단이 되기 쉽다.
설계
정의→근거→진단→설계→평가→증명 6단계, 위험등급별 자동 깊이조절. DESIGN 단계는 Workflow 재설계와 Tool-neutral Solution Design을 함께 다룹니다 — AI Workspace나 Agent 방식을 미리 정답으로 가정하지 않고, 업무 특성·데이터·보안·비용·운영조건을 고려해 SaaS·API·RPA·AI Agent·Custom Development 등 가능한 방식을 비교하고 필요한 조합을 설계하는 것을 원칙으로 삼습니다. 타 워크스페이스는 직접 수정하지 않고 승인 후 해당 워크스페이스 AI를 실행시킴.
현재 구조
DEFINE→EVIDENCE→DIAGNOSE→DESIGN(Workflow 재설계+도구중립 비교)→EVALUATE→PROVE, Risk Level L1~L4.
적용
Workspace·프로젝트 대상 13개 진단 사례 적용(세무·명리·부동산·투자·에이전트 실험실 등).
교훈
상시 자동화는 설계만으로 끝나지 않는다 — 독립 감사에서 실제 버그가 발견돼 수정 후 파일럿(수동 실행)으로 검증 중.
다음
시장 AI/자동화 기술지형과 실제 적용사례를 지속적으로 축적해 도구중립 비교 기준을 고도화하고 있습니다. 상시 리서치 자동화의 자동 트리거 전환도 현재는 의도적으로 보류 중입니다.
현재진단 Pipeline은 실사용 중, 상시 리서치 자동화는 검증 단계

LEGAL-WS — 고위험 지식업무를 AI Workflow로 어떻게 구조화했는가

High-stakes Knowledge Work Design
문제
AI가 자료를 대충 읽고 결론부터 내리면 고위험 업무에서 치명적이다.
설계
자료 접수 → 전체 인덱스 구축 → 1개씩 순서대로 완독하며 즉시 기록(병렬 처리 절대 금지) → 부족한 자료 확인 → 논점·리스크 정리 → 주요 주장과 근거에 원자료 출처를 연결한 초안 작성 → 역추적 검증 → 사람 검토 → 버전 관리.
현재 구조
완독 전 다음 단계 진행 자체를 막는 강제 구조.
적용
복수 유형의 실제 사건 업무에 적용 중.
교훈
강점은 사건 개수가 아니라, 고위험 지식업무를 순서·근거·검증·승인으로 통제한 Workflow 자체.
다음
산출물 아카이브 구조 정비.

AI-native Product Development Workflow

사업검증 → 제품기획·설계 → Multi-Agent 개발을 연결하는 End-to-End Workflow  ·  VTR-WS × PS-WS × DEV-WS

"더 빨리 코딩하기 위한 구조가 아니라, 잘못된 것을 빨리 만들지 않기 위한 구조."

문제
개발부터 시작하면 사업성·제품설계가 뒤늦게 따라온다.
설계
Business / Product / Development Context를 각각 독립 워크스페이스로 분리. PS는 코딩 권한을 의도적으로 배제.
현재 구조
VTR(Go/No-Go) → PS(제품설계) → DEV. 병렬개발이 필요한 경우 Claude가 PM/설계 역할로 작업을 독립 모듈로 분해하고, 작업량에 따라 가변적인 Codex CLI Worker가 각 모듈 구현을 맡습니다. (작업이 1~2개 수준으로 단순할 때는 별도 병렬화 없이 Claude가 직접 처리합니다.)
적용
VTR↔PS 실제 왕복(점술앱 프로젝트, 결제 인프라 제약이 사업전략을 실제로 재검토시킴) / DEV 병렬협업 실험.
교훈
Handoff는 발신만으로 완료되지 않는다 — 수신·적용까지 확인해야 한다.
다음
수신·적용 검증 자동화 + DEV→PS Feedback 강화.
현재VTR↔PS 흐름은 검증, DEV 연계는 계속 고도화 중
1~2개 작업 수준이면 병렬화 없이 Claude가 직접 처리. 정식 서브에이전트 4종은 지원·검증 역할.

실제 운영을 통해 얻은 설계원칙

완성 선언이 아니라, 실전에서 계속 쌓이는 원칙입니다.

01

업무부터 분석한다 — Automation보다 Process/Task 분해가 먼저

02

AI가 필요한 일만 AI에게 준다 — Rule/Cron/Agent/Human 구분

03

Context를 분리한다 — 업무마다 Workspace/Agent 경계

04

생성과 검증을 분리한다 — AI가 만든 결과를 다른 기준으로 평가

05

Handoff는 적용 확인까지다 — 보냈다는 것과 작동한다는 것은 다름

06

실패를 시스템에 남긴다 — Error → Learning → Rule → Skill

원칙 6개 더보기
  • 사람 판단은 제거가 아니라 중요한 결정에 집중시키는 것
  • "AI가 제안했다" ≠ "실제 적용됐다"
  • 반복지식은 Prompt보다 Rule·Skill·SOP로 축적
  • 외부·고위험 Agent는 최소권한과 Human Approval
  • 구축 후 Audit·변경관리 필요
  • AX는 시간절감뿐 아니라 새로운 업무·Insight 가능성도 본다
